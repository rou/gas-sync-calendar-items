# gas-sync-calendar-items

別ドメインの Google Workspace アカウント 2 つ（メイン / サブ）のカレンダー予定を、Google Apps Script で 15 分毎に双方向コピーする。どちらも同一人物のアカウント。

どちらのカレンダーを見ても埋まっている時間が一致する状態を作り、ダブルブッキングと「相手ドメインの同僚から見た空き時間のずれ」を防ぐのが目的。

詳細な仕様と設計判断の根拠は [docs/spec.md](docs/spec.md) にある。

初めて触るなら「現行スクリプトからの変更点」「仕組み」「移行手順」までを通して読む。「Script Properties」以降は必要なときに引く参照部。

---

## 現行スクリプトからの変更点

すでに稼働中の同期スクリプト（`syncShort` / `syncMid` / `syncLong`）を置き換える。現行を知っている人向けに、変わるところを先に挙げる。

| | 現行 | 新方式 |
|---|---|---|
| 同期方式 | ウィンドウ内のミラーを全削除して全再生成 | `updated` 比較による差分更新 |
| トリガー | 3 つ（short / mid / long） | **1 つ**（15 分毎） |
| 同期範囲 | 先 14 日 | **実行時点 〜 先 90 日** |
| `空き枠同期中` の予定 | 全削除の窓を塞ぐために必要 | **廃止**（窓が生まれないため） |
| 使う API | `CalendarApp` | Advanced Calendar Service（Calendar API v3） |
| ミラーの識別 | タイトルの `(自動生成)` のみ | `extendedProperties` ＋ タイトルの `(自動生成)` |
| 終日予定 | 除外していた | **コピーする** |
| 繰り返し予定 | 展開して単発予定としてコピー | **繰り返しルール（RRULE）ごとコピー** |

いちばん大きいのは同期方式の変更。現行はミラーにソース予定の ID を記録する場所がなかったため（タイトルしか使えなかった）、「このミラーは最新か」を判定できず全削除・全再生成しか選べなかった。トリガーの 3 分割・狭い同期範囲・`空き枠同期中` プレースホルダは、すべてこの制約から派生した回避策だった。

新方式ではミラーの `extendedProperties` にソースの ID と `updated` を持たせる。これで差分更新ができるようになり、上記が同時に解消する。

## できること

- 両アカウントの予定を相互にコピーする
- タイトル・本文・場所・時刻・繰り返しルール・色・空き/予定ありの区別を再現する
- ミラーは非公開（`visibility: private`）にするので、第三者には「予定あり」としか見えない。不在など、指定した種別だけ公開にもできる
- 不在（Out of office）とサイレントモード（Focus time）も、可能な範囲で同じ種別のままコピーする
- 通知用の予定（`【締切】` など）や共有目的の予定（`【共有】`）を除外する
- 両アカウントが同じ会議に招待されている場合は、二重に並ばないようミラーを作らない
- 辞退した予定はコピーしない

## できないこと

正直に書いておく。

- **参加者は同期しない。** ミラーには参加者を入れないので、ミラー側から出席者を確認できない。参加者を入れると二重招待になり、招待メールが飛んでしまうため意図的にそうしている
- **サイレントモードは同じ種別でコピーできない場合がある。** Workspace の一部エディション限定の機能で、かつ書き込み先の制約もある。コピーできない場合は通常予定に退避し、タイトルに `🎧` の目印を付ける。方向によって種別が揃わない可能性がある（メイン側は不在のまま、サブ側は通常予定など）
- **終わりのない繰り返し予定は、ミラーも同期範囲の外まで生える。** 繰り返しルールをそのまま転記する方式のため、同期範囲は「どの繰り返し予定を見つけるか」にしか効かない
- **同期範囲の外にある例外インスタンス（1 回だけ時間を変えた回など）は同期されない**
- **ミラーを手で編集しても上書きされる。** ソースが常に正。編集したい場合はソース側を編集する
- **Google Meet のリンクと添付ファイルはコピーしない。** 別の会議が作られてしまう／Drive の権限が別ドメインで開けないため。URL とファイル名は本文の末尾にテキストで補記する

## 仕組み：1 プロジェクトで両方向を処理する

メインアカウントで 1 つの GAS プロジェクトを実行し、共有されたサブのカレンダーを直接読み書きする。1 回の実行で両方向を処理する。

```
GAS プロジェクト（メインアカウントで実行）
  │
  ├─ syncOneWay(source = サブ,   target = メイン)
  └─ syncOneWay(source = メイン, target = サブ)
```

サブのカレンダーはメインに対して**予定の変更権限付き**で共有されている必要がある（現行スクリプトの稼働に必要だったものがそのまま使える）。

### ミラーの印

ミラーには 2 種類の印を付ける。役割が違うので両方必要。

| 印 | 役割 |
|---|---|
| `extendedProperties.private` | ループ防止 ＋ **差分更新**（ソースの ID と `updated` を格納） |
| タイトル末尾の ` (自動生成)` | ループ防止の安全弁 ＋ **人間がカレンダーを見て判別できる** |

`extendedProperties` だけだとカレンダー上でどちらが実体か分からない。タイトルだけだとソースの ID を記録できず差分更新ができない。

本文（`description`）には印を入れない。予定の内容を素のまま再現するため。

## セットアップ

### 1. GAS プロジェクトを作る

メインアカウントで [script.google.com](https://script.google.com) から新規プロジェクトを作成し、スクリプト ID を控える（プロジェクトの設定 → 「スクリプト ID」）。

### 2. clasp を設定する

```sh
npm install
npx clasp login          # GAS プロジェクトを所有するアカウントでログイン
```

clasp は 3.x を使う（`package.json` で固定）。別バージョンの clasp でログインした `~/.clasprc.json` は形式が違って読めず、`Cannot read properties of undefined (reading 'access_token')` になる。その場合は `npx clasp login` でログインし直す。

`.clasp.json.example` を `.clasp.json` にコピーし、控えたスクリプト ID を書く（`.clasp.json` は git 管理外）。

```json
{ "scriptId": "＜スクリプトID＞", "rootDir": "dist" }
```

### 3. デプロイする

```sh
npm run push             # build してから clasp push
```

### 4. Advanced Calendar Service を確認する

`appsscript.json` に定義済みなので自動で有効になる。GAS エディタの「サービス」に **Calendar API v3** が入っていることを確認する。

### 5. Script Properties を設定する

GAS エディタの プロジェクトの設定 → スクリプト プロパティ で設定する。最低限 `SUB_CALENDAR_ID` だけ必須。

### 6. 初回認可と設定確認

GAS エディタから `showConfig` を手動実行し、権限の承認画面を通す。読み込まれた設定が JSON で表示されるので、`subCalendarId` などを確認する。

## 現行スクリプトからの移行手順

この順序を必ず守ること。旧ミラーが 1 件でも残っていると、新スクリプトがそれを「普通の予定」とみなして相手側にコピーし、そのコピーがまた元に戻り、**予定が無限に増殖する**。旧ミラーを消しきってから新方式を動かす。

```
1. 旧トリガーを停止
   現行プロジェクトのトリガー一覧から syncShort / syncMid / syncLong をすべて削除する

2. 削除対象を確認（dry-run）
   DRY_RUN = true にして purgeLegacyMirrors を実行
   → ログに削除対象のタイトルと日時が一覧で出る。想定外のものが混じっていないか確認する

3. 旧ミラーを削除
   DRY_RUN = false にして purgeLegacyMirrors を実行

4. 新方式を確認（dry-run）
   DRY_RUN = true にして sync を実行
   → ログに作成予定の一覧が出る

5. 初回同期
   DRY_RUN = false にして sync を実行
   → 90 日分を作るため、カーソル継続実行で数回に分かれる場合がある
     ログの cursor が一巡するまで繰り返す

6. トリガーを設置
   installTrigger を実行（15 分毎の時間主導トリガーが 1 つ作られる）
```

`purgeLegacyMirrors` が削除するのは、両カレンダーにある以下の予定。**実行時点より先の予定だけ**を対象にし、過去分は履歴として残す（走査範囲は先 1 年まで）。

- タイトルが `(block)` に完全一致
- タイトルが `(自動生成)` で終わる
- タイトルが `空き枠同期中` に完全一致

なお旧マーカーの判定は移行後もコードに残す。取りこぼしがあったときの安全弁として、これらは常にミラー扱い（＝コピー対象外）にする。

## Script Properties

| キー | 既定値 | 説明 |
|---|---|---|
| `SUB_CALENDAR_ID` | **必須** | サブアカウントのメールアドレス |
| `SYNC_TAG` | `calendar-sync/v1` | ミラーの印に使うタグ値 |
| `WINDOW_PAST_DAYS` | `0` | 同期範囲の過去側（日数）。0 なら実行時点より前の予定は見ない。進行中の予定は含まれる |
| `WINDOW_FUTURE_DAYS` | `90` | 同期範囲の未来側（日数） |
| `EXCLUDE_TITLE_PATTERNS` | 下記 | 除外するタイトルの正規表現。`;` 区切り（JSON 配列でも可） |
| `MIRROR_TITLE_SUFFIX` | ` (自動生成)` | **変更するとカレンダーにゴミが残る**（下記参照） |
| `FALLBACK_PREFIX_OOO` | `🏖 ` | 不在を通常予定に退避したときの目印 |
| `FALLBACK_PREFIX_FOCUS` | `🎧 ` | サイレントモードを通常予定に退避したときの目印 |
| `APPEND_SOURCE_LINKS` | `true` | Meet URL と添付ファイル名を本文末尾に補記する |
| `DEFAULT_VISIBILITY_EVENT_TYPES` | なし | ミラーを非公開にせず、カレンダーの共有設定に従わせる種別。`default` / `outOfOffice` / `focusTime` を `;` か `,` で区切る。不在だけ公開するなら `outOfOffice` |
| `DRY_RUN` | `false` | 書き込みせずログだけ出す |
| `NOTIFY_EMAIL` | 実行アカウント | エラー通知の宛先 |
| `DEBUG_TITLE` | なし | `explain` で調べる予定のタイトルの一部 |
| `SYNC_CURSOR` | 自動管理 | 継続実行の進捗。**消すと初回同期をやり直せる** |
| `EVENT_TYPE_FALLBACK_CACHE` | 自動管理 | 種別書き込みの失敗キャッシュ |

`EXCLUDE_TITLE_PATTERNS` の既定値（5 パターン）:

```
^【締切】;^【対応依頼】;^【本日中】;^【AM締切】;【共有】
```

前 4 つは現行スクリプトの通知系除外の移植。5 つ目は今回の追加。スクリプト プロパティの入力欄は 1 行なので `;` で区切る。`;` の前後の空白は無視される。パターン自体に `;` を含めたいときは JSON 配列（`["a;b", "^【締切】"]`）で書く。

**設定すると既定値は上書きされる**（マージされない）。追加したいときは既定の 5 パターンも含めて書く。

`MIRROR_TITLE_SUFFIX` を変えると、旧サフィックスのミラーがどこからも参照されない孤児として残る。変更する場合は先に `purgeLegacyMirrors` で掃除する。

## 運用

### ログの読み方

実行ごとに 1 行のサマリが出る（GAS エディタの「実行数」または Cloud Logging）。

```
sync done  created=3 updated=1 deleted=0 skipped=42 (title-pattern=30 duplicate=7 declined=5) failed=0  1.8s  cursor=done
```

| 項目 | 意味 |
|---|---|
| `created` | 新しく作ったミラーの数 |
| `updated` | ソースの変更に追随して更新したミラーの数 |
| `deleted` | ソースが消えた／除外対象になったため削除したミラーの数 |
| `skipped` | 除外ルールに該当した、または変更がなかった予定の数 |
| `failed` | 処理に失敗した予定の数。**0 でないときはメール通知が飛ぶ** |
| `cursor` | 次回どこから処理を再開するか |

変更がない 15 分間隔の実行では `created` / `updated` / `deleted` がすべて 0 になるのが正常。

### 同期を止める

`removeTrigger` を実行するとトリガーが削除される。ミラーはそのまま残るので、消したい場合は `purgeAllMirrors` を使う（旧マーカー・新マーカーの両方を消す）。

一時的に止めたいだけなら `DRY_RUN` を `true` にする。

### トラブルシュート

#### 予定が増殖している → すぐ止めて、ミラーの印を確認する

ミラーの印が機能していない。`removeTrigger` で止めてから、以下を確認する。

1. ミラーの `extendedProperties` に `csTag` が入っているか（GAS エディタから `events.get` して確認）
2. タイトル末尾に ` (自動生成)` が付いているか
3. `MIRROR_TITLE_SUFFIX` を最近変えていないか

#### 特定の予定だけコピーされない → `explain` で判定の内訳を見る

スクリプト プロパティ `DEBUG_TITLE` に調べたい予定のタイトルの一部を入れ、`explain` を実行する。両カレンダーからその予定を探し、除外ルール・重複判定・既存ミラーの有無を段階ごとにログに出す。

よくある原因は重複判定。両アカウントが同じ会議に招待されている（同じ `iCalUID` が両方にある）場合、すでに両方のカレンダーに実体があるのでミラーは意図的に作らない。

#### 同期されない → トリガー・`DRY_RUN`・共有権限の順に確認する

1. トリガーが設置されているか
2. `DRY_RUN` が `true` になっていないか
3. `SUB_CALENDAR_ID` が正しいか
4. サブのカレンダーの共有権限が「予定の変更権限」以上か
5. ログの `skipped` が多い場合、除外ルールに引っかかっている可能性がある。`EXCLUDE_TITLE_PATTERNS` を確認する
6. 同じ会議が両カレンダーにある場合は、重複判定により意図的にミラーを作らない

#### 初回同期をやり直したい → `SYNC_CURSOR` を削除する

`SYNC_CURSOR` を削除すると、次回の実行で同期範囲の先頭から走り直す。既存のミラーは差分更新されるので二重にはならない。

#### 不在やサイレントモードが通常予定になっている → フォールバックのキャッシュを削除する

書き込み先のカレンダーでその種別が使えなかったということ。`EVENT_TYPE_FALLBACK_CACHE` に記録されている。エディションを変えた／制約が変わったなどで再試行したい場合は、このプロパティを削除する。

## 開発

```sh
npm test             # vitest
npm run typecheck    # tsc --noEmit
npm run build        # esbuild で dist/bundle.js にバンドル
npm run push         # build してから clasp push --force
```

`--force` は `appsscript.json` の上書き確認プロンプトを省くためのもの。マニフェストはリポジトリ管理なので、リモート側を上書きするのが正しい。push 対象は `dist/` の 2 ファイル（`bundle.js` と `appsscript.json`）だけで、`.clasp.json` の `rootDir` で絞っている。

TypeScript は esbuild で 1 ファイルにバンドルしてから push する。clasp のネイティブ TypeScript サポートは `import` / `export` が使えないため、モジュール分割と単体テストが成立しない。

Calendar API への呼び出しは `CalendarGateway` インターフェース越しに行う。テストでは [tests/fakeGateway.ts](tests/fakeGateway.ts) のインメモリ実装に差し替え、同期エンジンを GAS なしで丸ごと動かしている。作成・差分更新・削除・ループ防止・重複判定・繰り返しの例外追随・フォールバック・カーソル継続は、すべてこの偽物の上で検証している。

実機でしか確かめられない挙動（spec §17 の S1〜S4）は `spikeS1`〜`spikeS4` を GAS エディタから実行してログを読む。

同期ロジックを変更したら、実機で「連続 2〜3 回実行して `created` が 0 のまま」を**必ず確認する**。ここが増え続けるならループ防止が壊れている。

コード構成と設計判断の根拠は [docs/spec.md](docs/spec.md)、作業時の制約は [CLAUDE.md](CLAUDE.md) を参照。
